# LanDrop 电视收发与 LocalSend 默认兼容待办

更新日期：2026-11-06。定位：面向 Android TV 的局域网文件、文件夹、文本和剪贴板收发工具，手机上的 LocalSend 作为收发对端，不维护 LanDrop 手机界面。

**目标：LanDrop 已提供的收发功能，默认与原版 LocalSend 双向互通；允许 LanDrop 缺少其他功能，但不能要求用户修改 LocalSend 设置、转换内容或改用手动地址来完成正常互传。**

本文件是待办和验收要求，不代表当前实现已达到目标。TV 界面已按设计稿实施；本文件继续追踪未完成的协议与实机验收，界面实现不代表这些事项已通过。

## 1. 需求边界

- “兼容”要求内容、流程、结果正确，不要求复制 LocalSend 的全部界面和功能。未实现功能应明确缺失、不错误声明支持；缺失不影响其他已支持功能。
- 普通文件、图片、视频、APK、多文件、文件夹、文本、链接和剪贴板是本轮核心收发范围。发送入口可以不同，但已有入口不能出现单向可用、目录拍平、内容丢失或伪成功。
- **以原版默认配置为主验收基线，包括默认开启的 HTTPS。此前“原版关闭加密后才验收”的限制由本次需求替代。**原版 HTTP 模式也要兼容，但不能把关闭加密作为正常使用步骤。
- LanDrop 内部补齐必要的 HTTPS 连接和协议协商，不恢复加密设置项，也不让电视用户选择证书或传输协议。是否为本地接收监听增加 HTTPS，按下面的双向矩阵验证后选择必要实现，不预先要求重建完整加密功能界面。
- 电视优先：方向键、确认、返回可独立操作；默认后台接收、保留开机自启；收到内容先确认，取消或拒绝不落盘、不复制到剪贴板。
- 点击图标直接进入 TV 接收状态页，附近设备仅在主动选择内容后展示；选择文件、读取剪贴板和发送均为用户主动动作，不在启动时自动执行。
- 发送选择发现的在线设备，不提供手动地址输入入口。采用已确认的 TV 接收状态主页、纸飞机图标和明暗主题，附近设备仅在主动发送后展示。
- 默认文件保存到 `Download/localsend/`，保留用户选择其他目录的能力。不扩大存储权限范围，不用所有文件访问权限绕过电视缺少系统选择器的问题。
- 不承诺所有历史版本或无法互访的网络均可用；记录兼容的原版版本与设备。容器检查不能代替真实双机验收。

## 2. 功能兼容矩阵

以下“必须”均需 LocalSend → LanDrop、LanDrop → LocalSend 两个方向验证，原版保持默认配置。

| 内容或能力 | 本轮要求 | 完成标准 |
| --- | --- | --- |
| 自动发现、设备注册 | 必须 | 无需输入 IP，双方发现并选择对方；协议、端口、身份和版本协商正确 |
| 普通文件、未知扩展名、APK | 必须 | 逐字节正确保存；不能因电视没有打开该文件的应用而拒绝接收；APK 不自动安装 |
| 图片、视频、音频等媒体文件 | 必须 | 作为文件完整传输；相册分类、播放或预览可缺失，不影响保存 |
| 多文件 | 必须 | 接受、部分选择、拒绝、取消和结果清单与实际完成文件一致 |
| 文件夹、多层目录 | 必须 | 保留相对路径和不同目录下的同名文件，不静默拍平；明确空目录在原版协议中的表达能力 |
| 文本、链接 | 必须 | 按原版消息语义显示、确认和处理，不把消息强制保存成文本文件，也不把普通文本文件误当消息 |
| 剪贴板纯文本、链接 | 必须 | 用户主动发送，接收后可查看、复制；不自动覆盖剪贴板，不变成仅 LanDrop 识别的私有格式 |
| 剪贴板图片、文件 URI | 通过对应文件能力兼容 | 读取获授权内容后发送真实文件字节；不能把本地 `content://` URI 当作对方能读取的地址；访问失败需明确结束 |
| 富文本格式、剪贴板历史、后台自动同步 | 可缺失 | 不误报支持、不隐式监控或同步剪贴板；缺失不影响纯文本和文件收发 |
| PIN、确认、取消、异常清理 | 核心流程必须 | 原版启用可选 PIN 后流程仍能处理；拒绝、取消、失败不会报告成功或遗留可见半文件 |
| 收藏、网页分享/下载、多线程、断点续传、WebRTC/v3 | 可缺失 | 不宣告未实现能力；不因对端拥有这些功能而拒绝标准文件或消息请求 |

功能缺失允许没有入口或明确提示“不支持”；已有功能的协议不兼容、字节损坏、层级丢失、一直等待或伪成功属于缺陷，不能作为“精简功能”接受。

## 3. 源码审查基线与当前差距

当前主基线为本地 LocalSend **1.18.2+64，提交 `af0416be`，协议 2.2**；网络实现已迁移至 `packages/core` 的 Rust HTTP/组播核心，Dart 经 `packages/localsend_isolates` 桥接。LanDrop 当前仍声明协议 `2.0`。旧审查对象 `7f21d1f9`（协议 2.1）仅作为旧版回归参考，不再代表当前主基线。

必须沿真实网络调用链核对字段：Dart UI 的 `FileDto.hash` 经 `toRust()` 转为 Rust `FileDto.sha256`，线上 JSON 使用 `sha256`。不能只看 Dart 字段名推断新版本还发送 `hash`，也不能因构造时先写 `hash: null` 就认定最终不发送摘要。

| 差距或变化 | 当前代码事实 | 待办含义 |
| --- | --- | --- |
| 默认 HTTPS 与 mTLS | 原版默认 HTTPS；普通文件服务要求客户端证书，网页模式可放宽；TLS 注册声明的指纹与客户端证书不符时，不产生注册事件 | 已接入 AndroidKeyStore 客户端证书、统一 DER 指纹和服务端指纹核验；仍需 Android 5.0+ 签名提供方及真实原版验收；不能仅以注册返回 200 认定双方发现成功 |
| 传输方案 | 原版按目标声明的 HTTP/HTTPS 地址访问；LanDrop 本地仍监听 HTTP，已接受 HTTPS 对端声明；出站注册／传输／取消接入 mTLS 与指纹核验 | 区分本地监听协议与对端协议；默认互通不一定要求 LanDrop 本地改成 HTTPS，但连接原版 HTTPS 服务必须满足 mTLS |
| 发现 | 新 Rust 主要通过 `/v2/register` 探测和确认设备；组播只作 announcement，实际发包仍附 `announce: true` 兼容旧客户端 | 保留旧标志兼容，也覆盖 2.2 标准不带标志的广播；不能把收到 UDP 包或单边 HTTP 200 当成双向发现成功；LanDrop 现对无 announce 字段的 v2.2 广播也执行注册确认 |
| info 兼容入口 | 新原版仍提供 `/v1/info` 和 `/v2/info`，前者服务旧客户端探测；本版自身发现核心不再使用旧 Dart 的 v1 info 探测链 | v2 注册与发现优先；v1 info 仅按旧版目标需要补充，不再作为新版默认发现的主路径 |
| 校验和 | Rust 线上 DTO 使用 `sha256`；原版默认计算和验证摘要；Dart 的 `hash` 只是内部命名 | 与 LanDrop 当前线上字段已经一致；优先补双向实测及错误处理，不能再把“改成 hash”当修复；旧 2.1 兼容另测 |
| 校验失败与重试 | 原版返回 422；发送端针对 422 最多尝试 3 次，接收端允许同会话、同 token 的整文件重试 | LanDrop 已区分 422，保留同会话/token 并最多尝试三次，耗尽后清理；待实际验证重试字节和临时文件清理；这不等于需要做断点续传 |
| 待确认取消 | 新原版支持匹配发送方地址的无 `sessionId` 取消，并清理 pending 会话；连接中止也有生命周期保护 | 已支持按发送方地址取消未确认请求及关闭本地确认；仍需验证接受／取消竞态、断线和重试时序 |
| 文件夹与消息 | 原版保留相对路径，消息仍通过 `preview` 与 204 处理；LanDrop 已保留发送路径并按层级保存，加入路径越界检查；SAF、MediaStore 和旧存储分支需实机验收 | 文件夹、文本、链接和剪贴板继续列 P0，不能仅验单文件 |
| 确认超时 | LanDrop 发送读超时已调为 90 秒，接收确认窗口 60 秒 | 需要验证临近截止时确认、网络中断和取消的实际结果 |
| 验证 | 构建、单元测试与实际互通分别验收，执行方法见 [开发指南](development.md) | 原版测试和电视双机测试需单独记录，不能把本地构建结果视为互通通过 |

## 4. P0：默认配置下全面兼容已支持的收发内容

### P0-01 原版默认配置下的发现与传输连接

- [ ] 发现列表和注册流程接受原版的 HTTP、HTTPS 端点，发送、注册、探测、取消均按目标设备声明的协议访问。
- [ ] 区分“LanDrop 本地监听协议”“对端声明的监听协议”“本次请求使用的协议”。原版设备声明 HTTPS，不代表它不能按 LanDrop 广播的 HTTP 地址发送请求，不能仅因此返回 403。
- [ ] 补齐 mTLS 客户端：生成并持久保存本机证书与私钥，连接原版时出示客户端证书，并核验原版服务端证书指纹。不要求公共 CA，也不永久无条件信任所有证书；测试缺少客户端证书、指纹不匹配、证书变化与重启后的身份稳定性。
- [ ] TLS 注册的 `fingerprint` 与本机客户端证书 DER 的 SHA-256 一致；统一 HTTP 广播、注册、发送中的本机身份，避免 UUID 与证书指纹混用，导致同一设备被发现为两台或原版静默忽略注册。改名不更换身份。
- [ ] 先验证“LanDrop 广播 HTTP 接收地址、可连接原版 HTTPS 地址”的最小方案；若默认互通矩阵仍有缺口，再补必要的接收监听能力。不要把支持 HTTPS 出站误报为所有方向都已加密。
- [ ] 优先覆盖新版的 v2 注册探测、组播与 HTTP 确认、扫描回退；广播同时测试本版发送的 `announce: true` 与标准 2.2 无标志样本，避免应答循环。只有旧版目标需要时再验证 v1 info 初始探测兼容，避免无条件 HTTP 降级或来回猜协议。
- [ ] 测试两个启动顺序、手动刷新、设备重命名、IP 变化、网络切换及重复广播；自动发现不能依赖用户先手动输入地址。

验收：原版默认 HTTPS 与原版 HTTP 两种配置均能双向发现并互传，默认配置优先验收；不要求关闭加密，不增加协议选择界面。

### P0-02 双方协议契约与能力声明

- [ ] 从原版源码生成真实广播、info、注册、准备上传、文件描述、响应和取消样本，覆盖双方序列化与解析，不能只测 LanDrop 自己生成的数据。
- [ ] 以 1.18.2 的 Rust 线上 DTO 和协议 2.2 为主契约；覆盖 LanDrop 2.0 的实际能力，并将旧原版 2.1 作为单独回归对象。不要仅凭 Dart UI 模型确定 JSON 格式，也不盲目提高本机声明版本。
- [ ] 容忍协议允许的可选/未知字段、未知 MIME 类型和缺失元数据；文件名、大小、文件 ID、会话 ID、token 等关键字段按契约校验。
- [ ] 对照 `200/204/400/401/403/404/409/422/429` 等状态码语义，区分消息已处理、拒绝、忙碌、无会话、参数错误、摘要不匹配和 PIN 错误，不把所有结果都归为失败或成功。
- [ ] 缺少网页下载等能力时如实声明，例如不虚报 `download`；允许对端拥有额外能力，不将其作为拒绝普通收发的条件。

验收：双方能正确理解设备信息、文件描述、协商结果与失败原因；应用品牌、包名和界面精简不改变 LocalSend 协议字段及路径。

### P0-03 文件、文件夹、文本和剪贴板完整互通

- [ ] 文件发送描述只携带必要协议字段；发送和接收均流式处理，不因文件较大将整个内容加载入内存。
- [ ] 文件夹发送保留相对路径，接收在默认目录和用户授权目录下创建层级；保留根目录含义及不同目录下的同名文件。
- [ ] 拒绝绝对路径、`..` 等越界路径；定义重名处理与取消后的清理，不默认覆盖现有文件，不以删除目录部分冒充安全的文件夹支持。
- [ ] 文本、链接、剪贴板纯文本按原版消息语义处理，覆盖 `preview` 与 HTTP 204；区分普通 `.txt` 文件和文本消息，避免误存文件、重复上传或误判失败。
- [ ] 剪贴板中的获授权文件/图片 URI 转为实际文件内容；富文本或无法读取的内容明确提示支持范围，不虚报已经发送。
- [ ] 接收消息可查看、复制，打开链接是用户主动动作；没有可用剪贴板或处理程序的电视仍能查看结果，不自动打开、执行或安装接收内容。

验收：功能矩阵中的核心内容双向正确；二进制字节、文本内容、目录结构、选中文件集合和用户看到的结果一致。空目录等协议表达限制单独记录，不静默承诺。

### P0-04 新版 sha256 互认、422 重试与旧版回归

- [ ] 保留 2.2 线上 `sha256`，验证新原版计算摘要 → LanDrop 验证、LanDrop 计算摘要 → 新原版验证两个方向；不能因为 Dart 内部叫 `hash` 就改错线上字段。
- [ ] 如需覆盖旧原版 2.1，单独兼容 `hash` 样本；可支持接收别名，但两个字段同时存在且内容矛盾时不能静默接受，也不能因此改变 2.2 的发送字段。
- [ ] 区分“未提供摘要”“校验通过”“校验失败”；用户关闭摘要功能或摘要生成失败时，仍按对端真实请求处理，不虚报校验结果。
- [ ] 摘要不匹配与参数错误、拒绝分开返回；对齐 422 及同会话、同 token、同文件目标的整文件重试，覆盖新版原版最多 3 次尝试的行为，不重复发布文件或遗留半文件。
- [ ] 覆盖正确/错误/缺失摘要、空文件、截断、中断、重试成功和尝试耗尽；如 LanDrop 暂不主动重试，也要清楚报告失败并能处理对端合法重试，不能误报支持断点续传。

验收：2.2 双向摘要实测通过，422 和重试状态可互认；旧版兼容不破坏新版；未提供摘要不阻塞传输，不虚报完整性、加密或身份认证结果。

### P0-05 确认、PIN、取消及失败恢复

- [ ] 分离 `/prepare-upload` 确认等待与文件读写超时，保证当前 60 秒接收确认期内接受仍可继续，发送请求留出响应余量。
- [ ] 明确 PIN 输入、用户等待、网络无进展的各自截止条件；覆盖 35 秒后接受、拒绝、到期、正确/错误 PIN 及重试。
- [ ] 待确认时兼容新版无 `sessionId` 的 `/cancel`：只匹配对应发送方及待确认会话，其他设备不能取消当前请求；已建立会话时按 `sessionId` 取消。覆盖请求连接中止的清理，不自创私有字段。
- [ ] 清理待确认请求、会话、目标文件和进度；过期通知/弹窗不能接受新请求；第二个发送方不能覆盖当前确认或传输。
- [ ] 覆盖网络断开、空间不足、权限失效、存储被拔出和忙碌状态，恢复后能够继续处理下一次请求。

验收：拒绝、取消、过期和失败均能结束；双方对已完成的内容认识一致，没有伪成功、等待不结束或可见半文件。

### P0-06 真实双向互通矩阵与发布门槛

- [ ] 电视 LanDrop ↔ 原版 1.18.2 Android、电视 LanDrop ↔ 原版 1.18.2 桌面，均以原版默认 HTTPS/mTLS 配置验证；原版 HTTP、旧版 2.1 作为额外回归组合。

## 5. P1：电视操作与持续可用性

### P1-01 遥控器与后台接收确认

- [ ] 全流程方向键、确认、返回可完成，焦点清楚、顺序稳定；无必须触摸、长按或悬停的步骤。
- [ ] 文件请求显示设备、数量、总大小、可理解的列表；消息请求显示内容。保留确认默认聚焦拒绝的行为。
- [ ] 验证其他应用播放时的悬浮确认、返回拒绝、请求过期；无通知面板或无悬浮权限时明确可用入口，不声称系统禁止的后台弹窗可用。
- [ ] 检查 720p、1080p、4K、系统字体放大和浅深主题；采用 TV 接收状态主页与已确认的精简设置布局，不增加中间启动页面。

### P1-02 文件选择、授权和结果操作

- [ ] 优先系统选择器，缺失时使用已有内置浏览器；验证下载目录、授权目录、可访问 U 盘的文件/文件夹多选与返回。
- [ ] 撤销授权或无法读取时明确结束，不把不可访问目录显示为正常空目录，不扩大到所有文件访问权限。
- [ ] 接收结果区分文件保存位置和消息内容；可进入接收记录，查看、复制或打开均为主动动作。APK 不自动安装。

### P1-03 开机、待机、网络切换与资源释放

- [ ] 真实验证开机自启、延迟联网、待机恢复、有线/Wi-Fi 切换及应用更新；手动停止后不自动恢复，重新启用后才恢复。
- [ ] 网络恢复后重绑监听、释放旧套接字、重新广播和去重；改名不打断当前传输。
- [ ] 空闲不持有不必要的唤醒锁，结束后释放资源；长时间运行无重复通知、重复监听或持续内存增长。
- [ ] 区分关闭页面、系统回收、强行停止和深度待机，记录实际电视及厂商限制，不保证绕过系统限制。

构建、依赖安装、自动化测试和环境模拟均在容器内执行，沿用现有 Gradle Wrapper、JDK 17、Android SDK/AGP 配置。实际 CI、容器内 Android 测试和真实电视互通分别记录，不能相互替代。
